# Graph security boundary

Every repository method takes an explicit GraphScope. There is no default or public scope. All fixed Cypher reads/writes include the scope; UUID alone never grants access. The repository is a trusted internal service, not an authorization oracle: request code must derive scope through `app.graph_api.scoped_repository`. That dependency uses existing authenticated principal hashing, platform rate limiting and current Redis workspace membership. No untrusted body can override the principal or verification role. Shared API key mode intentionally remains one shared account, matching existing behavior. Redis outages cannot grant workspace access.

The graph API is read-only. Verification transitions and source verification are available only to trusted backend code with database credentials, never registered as agent/LLM tools. Reviewer transitions require actor/reason and expected revision. Verified assertions require located evidence pointing to verified immutable source snapshots. This checks provenance structure, not the truth of arbitrary supplied documents; a future source verification workflow must independently authenticate evidence before invoking these trusted methods. Confidence has no effect on status.

All user values use parameters; relationship/label tokens are static server-owned code. Entity names, URLs and passages never become Cypher syntax. No arbitrary query endpoint, dynamic LLM labels, APOC execution or database administration API is exposed. Bounded tuple/string sizes, strict enums, timezone validation, finite confidence, result limits, pool limits, platform rate limits and transaction timeouts constrain input and database resource use. JSON schemas are additive, with unknown fields rejected by leaf contracts.

Source URLs are metadata only, never fetched. Future-dated retrieval and entity metadata timestamps are rejected beyond a five-minute clock-skew allowance. Credential-bearing URLs are rejected; digests are validated SHA-256 strings. Private source content is not logged. Driver exceptions map to stable generic graph errors; credentials are SecretStr configuration and never embedded in URIs. No credentials appear in committed deployment files. Keep database networking private and credentials in environment/secret injection; use TLS for remote Bolt. Compose HTTP health is only a readiness probe, not proof of authorization or schema correctness.

Neo4j Community lacks per-tenant row-level security. A database administrator or arbitrary database credential holder can bypass application isolation; use separate database instances where hard isolation is required. Workspaces can be deleted or expire in Redis while graph records persist: authorization then denies reads, but physical graph deletion/retention is deliberately not automated in these phases. Plan audited retention before Phase 3. In-flight request authorization uses the membership snapshot checked at request admission, matching existing platform behavior.

Threats verified by tests: JWT/private scope isolation, workspace membership rejection, unknown workspace/private lookup denial, arbitrary mutation method rejection, graph-disabled auth, parameterized injection-shaped names, identity collisions, atomic rollback, lifecycle races, unsupported predicate/type rejection and redacted connection failure. Remaining deployment checks: Compose image startup on Docker, private-network/firewall policy, secret rotation, TLS and restore drills.
